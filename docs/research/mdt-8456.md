# MDT 8456 reference

This page records how Microsoft Deployment Toolkit (MDT) 8456 implements the features deployarr reproduces. Check it before you build a feature MDT also has, so deployarr keeps MDT's working behavior and avoids its known faults.

## Sources

- Microsoft no longer hosts the MDT 8456 installer. On 2026-11-11, `https://download.microsoft.com/download/3/3/9/339BE62D-B4B8-4956-B58D-73C4685FC492/MicrosoftDeploymentToolkit_x64.msi` returned HTTP 404.
- The scripts and templates come from `Source/MDT.8456` in [keithga/DeployShared](https://github.com/keithga/DeployShared), maintained by a former MDT developer. Paths on this page are relative to that folder. To get them, run `git clone --depth 1 https://github.com/keithga/DeployShared`.
- The native helper `Microsoft.BDD.Utility.dll` comes from hotfix KB4564442 (`MDT_KB4564442.exe`, SHA-256 `cd0bc2ec616ba5f8ddd626d02747b19c90efa1ba159303f2ff41ae693ec10b3f`). That download still works. We analyzed the DLL with REA and Ghidra 12.1.4.
- The task sequence engine (`TsManager.exe`, `TsmBootstrap.exe`, `TsCore.dll`) is closed-source ConfigMgr code that ships only in the MSI. This page describes it from the scripts' side. [MDT 8450 binaries reference](mdt-8450-binaries.md#task-sequence-engine) describes it from its own code, and confirms or corrects the items this page once marked as inferred.

## Task sequence format

A task sequence is an XML tree. `Templates/Client.xml` is the standard client sequence.

| Element | Attributes and children | Source |
| --- | --- | --- |
| `<sequence>` | `version="3.00"`, `name`, `description`, optional `<globalVarList>` | `Templates/Client.xml:2-11` |
| `<group>` | `name`, `description`, `disable`, `continueOnError`, `expand` (UI only), one optional `<condition>`, nested groups and steps | `Templates/Client.xml:12, 77-115` |
| `<step>` | `type`, `name`, `description`, `disable`, `continueOnError`, `successCodeList`, `runIn` (`WinPE` or `WinPEandFullOS`), `startIn`. Children are `<condition>`, `<defaultVarList>`, and `<action>` | `Templates/Client.xml:61-70, 189, 55` |
| `<defaultVarList>` | `<variable name="OSDDiskIndex" property="DiskIndex">0</variable>`. The engine applies these as fallback values before it evaluates the step's condition and removes them when the step ends | `Templates/Client.xml:157`, `TsManager!0x140033c10` |
| `<condition>` | `<expression>` elements, or `<operator type="and\|or\|not">` that nest | `Templates/Server.xml:465-481` |

Condition expression types:

| Type | Parameters | Example |
| --- | --- | --- |
| Variable | `Variable`, `Operator`, `Value` | everywhere |
| Registry | `KeyPath`, `Value`, `Type`, `Operator`, `Data` | `Templates/ClientUpgrade.xml:47-53` |
| WMI | `Namespace`, `Query`. True if the query returns any rows | `SCCM/SCCM_Client.xml:41-44` |
| File | `Path` | `SCCM/SCCM_Client.xml:51-53` |
| Folder | `Path` | `SCCM/SCCM_Server.xml:471-473` |

The operators used in the templates are `equals`, `notEquals`, `exists`, `notExists`, and `greaterEqual`.

In Lite Touch, every step's real work is its `<action>` command line, usually `cscript.exe "%SCRIPTROOT%\<script>.wsf"`. The `type` attribute mostly selects the editor page. The types in `Client.xml` are `BDD_Gather`, `BDD_Validate`, `SMS_TaskSequence_RunCommandLineAction`, `SMS_TaskSequence_RebootAction`, `SMS_TaskSequence_PartitionDiskAction`, `BDD_InjectDrivers`, `BDD_InstallUpdatesOffline`, `BDD_InstallOS`, `BDD_RecoverDomainJoin`, `BDD_InstallApplication`, and `SMS_TaskSequence_EnableBitLockerAction`.

## Phases

`Client.xml` has six top-level groups. Each one tests the `PHASE` variable with `equals` (`Templates/Client.xml:22-30, 48-54`).

1. Validation
2. State Capture
3. Preinstall. In this group, a "New Computer only" subgroup partitions the disk.
4. Install
5. Postinstall
6. State Restore

`ZTINextPhase.wsf:74-91` advances `PHASE` in a fixed order. A fresh boot into WinPE starts at `PREINSTALL` (`LiteTouch.wsf:371-391`). Phases exist because the engine evaluates a group's condition when it reaches the group, so after a reboot the next group sees the updated value.

## Engine launch, state, and resume

- WinPE starts `bddrun.exe /bootstrap` from `winpeshl.ini`. The PE unattend file then runs `wscript.exe X:\Deploy\Scripts\LiteTouch.wsf` (`Templates/winpeshl.ini:1-2`, `Templates/Unattend_PE_x64.xml:11-17`).
- `LiteTouch.wsf` writes `TS.XML` only if it does not exist yet, so the sequence is frozen at first launch. Sub-sequences are inlined as groups (`LiteTouch.wsf:792-809, 1729-1833`).
- State lives in `MININT` and `_SMSTaskSequence` on the first suitable local drive. Before the disk is partitioned, that drive is `X:` (`ZTIUtility.vbs:1782-1841`).
- Variables persist in `VARIABLES.DAT`, an XML file with upper-cased names, protected by a `VARIABLES.DAT.LOCK` file. Credential variables are only base64-encoded (`ZTIUtility.vbs:943-1099`).
- The engine tracks progress with an instruction pointer, `_SMSTSNextInstructionPointer` (`ZTIUtility.vbs:278-285`). The engine runs the tree as a flat table of group-begin, group-end, and step entries (`TsCore!0x18019d2b8`).
- A step asks for a reboot by setting `SMSTSRebootRequested=true` and exiting 0. Setting `SMSTSRetryRequested=true` as well makes the same step run again after the reboot (`LTIApply.wsf:540`, `ZTIApplications.wsf:131-140`).
- The engine exits with `-2147021886` (`0x80070BC2`) to ask the wrapper for a reboot (`LiteTouch.wsf:874`, `TsManager!0x140023876`). In WinPE the wrapper exits, which ends the shell and reboots the PC.
- In the full OS, MDT resumes through auto-logon. The new OS's unattend enables the built-in Administrator with `AutoLogon` and `LogonCount 999`. `FirstLogonCommands` then run `LTIBootstrap.vbs`, which starts `LiteTouch.wsf`. Later reboots go through a `LiteTouch.lnk` startup shortcut (`Templates/Unattend_x64.xml.10.0:126-148`, `LiteTouch.wsf:1426-1520`).
- `LTICleanup.wsf` removes auto-logon and the `DefaultPassword` value, deletes `MININT`, `_SMSTaskSequence`, and `VARIABLES.DAT`, and archives logs to `%SystemRoot%\Temp\DeploymentLogs` (`LTICleanup.wsf:98-505`).

## Logging

MDT writes CMTrace-format lines to `<script>.log` and to `BDD.log` (`ZTIUtility.vbs:194-223`):

```
<![LOG[message]LOG]!><time="HH:MM:SS.000+000" date="MM-DD-YYYY" component="Script" context="" type="1" thread="" file="Script">
```

Type 1 is info, 2 is warning, and 3 is error. Any message that contains "password" is replaced with a placeholder. Logs are also copied to the `SLShare` network share, and progress events go to a monitoring web service (`ZTIUtility.vbs:290-421, 463-640`).

## Rules and database lookup

`ZTIGather.wsf` evaluates rules from `Bootstrap.ini`, then `CustomSettings.ini`.

- `[Settings] Priority=` lists sections in order. An entry that names a property with a value jumps to the section named after that value, so `Priority=Model` reads `[Latitude 7450]`. A list property such as `MacAddress` tries one section per value (`ZTIGather.wsf:1403-1473`).
- For a scalar property, the first non-empty value wins. A few properties, such as `DeployRoot` and `Phase`, are marked overwrite, so the last value wins. List properties (`Applications001`, `Applications002`, and so on) collect unique values from every section (`ZTIGather.wsf:1925-1947`, `ZTIGather.xml:6-14`).
- `%Prop%` substitutes a value. `#expr#` runs arbitrary VBScript through `Eval` (`ZTIUtility.vbs:1266-1348`).
- A section with `SQLServer=` is a database query. `Parameters=` names the properties to match, `ParameterCondition=` joins them with `AND` or `OR`, and `Table=` or `StoredProcedure=` names the source. Each column of the result sets the property with the same name (`ZTIDataAccess.vbs:104-165`, `ZTIGather.wsf:1672-1730`).
- The query is built by string concatenation, `sColumn & " = '" & tmpValue & "'"`, with no escaping (`ZTIDataAccess.vbs:501-567`). The full connection string, password included, is written to the log (`ZTIDataAccess.vbs:438`). A connection or query failure is only logged, and the deployment continues (`ZTIGather.wsf:1631-1644`).
- A section with `WebService=` calls a URL with the same parameters and maps the XML reply by element name (`ZTIDataAccess.vbs:739-999`).

A rules chain that looks up an order and maps its OS code to a task sequence:

```ini
[Settings]
Priority=OrderDB, OSCode, Default
Properties=OrderNumber, OSCode

[OrderDB]
SQLServer=SQL01
Database=Sales
Table=dbo.Orders
Parameters=OrderNumber
OrderNumber=ORDER_NO
OSCode=OS_ID

[W11ENT]
TaskSequenceID=W11ENT-X64
SkipTaskSequence=YES
```

MDT has no step that asks for input and then runs the rules again. The rules run before the wizard (`LiteTouch.wsf:519-586`).

## Task sequence selection

- When the rules set `TaskSequenceID` and `SkipTaskSequence=YES`, the wizard skips the selection page (`DeployWiz_Definition_ENU.xml:33-35`).
- When `TaskSequenceID` is set and the page is shown, the page pre-selects that sequence. Next stays disabled until something is selected (`DeployWiz_SelectTS.vbs:48-83`).
- The list hides sequences with `hide="True"` or `enable="False"`, groups them by folder, and filters by architecture and supported platform (`ZTIConfigFile.vbs:636-659`, `DeployWiz_Initialization.vbs:42-124`).
- A fully unattended run needs `SkipBDDWelcome=YES`, `SkipWizard=YES` (or every `Skip*` page property), credentials in `Bootstrap.ini`, and `SkipFinalSummary=YES` (`LiteTouch.wsf:438, 582-634, 961-967`).

## Gathered facts

`ZTIGather.wsf` reads hardware facts through WMI. The facts that zero-touch deployments key on are these:

| Property | Source | Lines |
| --- | --- | --- |
| `SerialNumber` | `Win32_BIOS` (SMBIOS type 1, the system serial) | `ZTIGather.wsf:437-446` |
| `Product` | `Win32_BaseBoard` (SMBIOS type 2) | `ZTIGather.wsf:577-586` |
| `Make`, `Model`, `Memory` | `Win32_ComputerSystem` | `ZTIGather.wsf:540-553` |
| `UUID` | `Win32_ComputerSystemProduct` | `ZTIGather.wsf:564-571` |
| `AssetTag`, `IsLaptop`, `IsDesktop` | `Win32_SystemEnclosure` | `ZTIGather.wsf:403-429` |
| `MacAddress`, `IPAddress`, `DefaultGateway` | `Win32_NetworkAdapterConfiguration` | `ZTIGather.wsf:973-1018` |
| `IsUEFI` | `Microsoft.BDD.Utility` COM object | `ZTIGather.wsf:594-597` |
| `IsVM` | Make and Model strings | `ZTIGather.wsf:1228-1309` |

MDT never reads the baseboard serial number.

## Drivers

- `ZTIDrivers.wsf` gets every device's hardware and compatible IDs from a separate tool, `Microsoft.BDD.PnpEnum.exe`, not from WMI (`ZTIDrivers.wsf:1265-1277`).
- Each catalog entry lists the PnP IDs its INF supports. Matching is an exact, case-insensitive string compare. Every package that matches any device ID is copied, with no ranking (`ZTIDrivers.wsf:339-376, 1299-1324`).
- `DriverInjectionMode=ALL` copies every driver in the selected group or selection profile, whatever the hardware (`ZTIDrivers.wsf:151-169`).
- The catalog schema has an `OSVersion` field, but `ZTIDrivers.wsf` never reads it. A driver with no `Platform` element is always skipped (`ZTIDrivers.wsf:1244-1259`).
- Drivers are copied to `C:\Drivers`. `LTIApply.wsf` then runs `dism /Image:C:\ /Apply-Unattend`, and the unattend's `offlineServicing` pass points `PnpCustomizationsNonWinPE` at `\Drivers`. This one DISM call injects drivers and packages together, so one bad driver fails the deployment (`LTIApply.wsf:1021-1046`, `Templates/Unattend_x64.xml.10.0:168-176`).
- Nothing checks for devices that still have no driver at the end.
- WinPE gets network and storage drivers from a separate boot-image setting (`Templates/Settings.xml:37-51`).

## OS install and disk layout

- For a clean install, MDT always applies a WIM: `DISM.exe /Apply-Image /ImageFile:"<wim>" /Index:<n> /ApplyDir:C:` (`LTIApply.wsf:915-926`). An OS imported from an ISO still has its `install.wim` applied. `ApplySetup`, the `setup.exe` path, has no caller (`LTIApply.wsf:553`). `setup.exe` is used only for in-place upgrades.
- On BIOS, MDT writes boot files with `bootsect.exe /nt60` and then `bcdboot.exe C:\windows /l <UILanguage> /s S:`. On UEFI, it deletes the old BCD store and runs `bcdboot.exe C:\windows /l <UILanguage>` with no `/s` or `/f`. An empty `UILanguage` aborts the run (`LTIApply.wsf:935-1006`, `ZTIDiskUtility.vbs:514-532`).
- Default UEFI layout is EFI 499 MB FAT32, MSR 128 MB, Windows at 99% of the rest, and Recovery with the remainder, on GPT. The BIOS layout is a 499 MB active "System Reserved" partition, Windows, and Recovery, on MBR (`Templates/Client.xml:157-234`).
- `ZTIDiskpart.wsf` pipes a generated script into `diskpart` with no per-command error checks. It rejects USB disks, except USB 3.0 disks (`ZTIDiskpart.wsf:296-536`, `ZTIDiskUtility.vbs:71-94`).

## Applications

- The catalog fields are `Name`, `Version`, `Publisher`, `Source`, `CommandLine`, `WorkingDirectory`, `SupportedPlatform`, `UninstallKey`, `Dependency`, and `Reboot` (`Templates/Applications.xsd:7-29`).
- `MandatoryApplications` install first, then `Applications`. Dependencies install recursively, with cycle protection (`ZTIApplications.wsf:151, 342-364`).
- An app counts as already installed if its `UninstallKey` exists under the `Uninstall` registry key (`ZTIApplications.wsf:309-336`).
- Success codes default to `0 3010`. Any other exit code is logged, the app is still added to `InstalledApplications`, and the deployment continues. Exit code 3010 does not cause a reboot. Only `<Reboot>True</Reboot>` does (`ZTIApplications.wsf:455-486`).

## Unattend

`ZTIConfigure.wsf` writes variables into the unattend file through XPath mappings in `ZTIConfigure.xml`. The mapped values include `OSDComputerName`, `ProductKey`, `JoinDomain`, `AdminPassword`, `TimeZoneName`, `KeyboardLocale`, `UserLocale`, and `UILanguage` (`ZTIConfigure.xml:103-216`). The whole routine runs under `On Error Resume Next`, so a failed mapping goes unnoticed (`ZTIConfigure.wsf:99`). Passwords are written with `PlainText=true`.

## WinPE

`Templates/LiteTouchPE.xml` adds the optional components `winpe-hta`, `winpe-scripting`, `winpe-wmi`, `winpe-securestartup`, and `winpe-fmapi`, because the scripts and the wizard need them (`LiteTouchPE.xml:13-17`). The `Bootstrap.ini` template is empty. For an unattended run, admins add `DeployRoot`, `UserID`, `UserDomain`, and `UserPassword` to it, and the boot image build copies the file into `X:\Deploy\Scripts` in plain text (`Templates/Bootstrap.ini:1-4`, `LiteTouchPE.xml:28-101`).

## Native helper DLL

`Microsoft.BDD.Utility.dll` is a COM in-process server. It exports only `DllGetClassObject` and the other three COM entry points. The scripts call `IsUEFI`, `IsHypervisorRunning`, `Is64Bit`, `Supports64Bit`, `SupportsNX`, `SupportsVT`, `HiddenPartitionsToDrives`, `KeepAlive`, `WaitForShell`, and `IsAdmin` on it. `WaitForShell` is missing from the type library, so that call fails silently. [MDT 8450 binaries reference](mdt-8450-binaries.md#microsoftbddutilitydll) describes every method.

In the 8456 hotfix build, `IsUEFI` (function `FUN_18000cb54` in the x64 build) works like this:

1. It enables `SeSystemEnvironmentPrivilege` on the process token.
2. It resolves `GetFirmwareEnvironmentVariableW` at run time and calls it with an empty variable name and the GUID `{00000000-0000-0000-0000-000000000000}`.
3. If that call fails with any error except `ERROR_INVALID_FUNCTION` (1), the firmware is UEFI. Legacy BIOS returns `ERROR_INVALID_FUNCTION`.

The 8450 build skips step 1. Enabling the privilege is the hotfix's only change.

`KeepAlive` calls `SetThreadExecutionState` to stop the PC from sleeping.

## MDT faults that deployarr fixes

| MDT behavior | Evidence | deployarr decision |
| --- | --- | --- |
| SQL values pasted into the query string | `ZTIDataAccess.vbs:556` | Parameterized queries only |
| Database password written to the log | `ZTIDataAccess.vbs:438` | Credentials stay on the server. Logs redact secrets |
| Database failure only logged, and the run continues | `ZTIGather.wsf:1631-1644` | A lookup error stops at a clear prompt or fallback |
| Unattended runs need share credentials in the boot image | `Templates/Bootstrap.ini`, `LiteTouchPE.xml` | The boot image holds only the server URL and CA certificate |
| Auto-logon as Administrator for 999 logons to resume | `Templates/Unattend_x64.xml.10.0:126-135` | The agent resumes as a Windows service, with no auto-logon |
| Driver OS version never checked | `ZTIDrivers.wsf` has no `OSVersion` read | INF decorations filter by architecture and OS build |
| One DISM call injects all drivers, and one bad driver fails the run | `LTIApply.wsf:1044` | Inject one driver package at a time and record each result |
| No check for missing drivers at the end | none | A final step lists devices with no driver and applies the configured policy |
| Unexpected app exit codes treated as success | `ZTIApplications.wsf:465-474` | Unexpected exit codes fail the step |
| Exit code 3010 ignored | `ZTIApplications.wsf:478-486` | 3010 and 1641 mean success plus a reboot |
| UEFI `bcdboot` without `/s` or `/f` | `LTIApply.wsf:978` | `bcdboot W:\Windows /s S: /f UEFI` or `/f BIOS`, explicitly |
| `#expr#` runs arbitrary VBScript | `ZTIUtility.vbs:1266-1348` | Conditions use a small typed expression language |
| Unattend mapping under `On Error Resume Next` | `ZTIConfigure.wsf:99` | The server renders and validates the unattend file before it sends it |
